# Run [backend/supabase/001_reports.sql](backend/supabase/001_reports.sql) in the project's Supabase SQL Editor as the database owner before using assessments. It assumes the existing `public.assessments` table has UUID `id` / `user_id`, JSON `answers` / `domain_scores`, and `completed_at`, `total_score`, `risk_level` columns.

Administrator report access uses the existing `public.profiles.role` assignment, looked up by the backend with `SUPABASE_SERVICE_ROLE_KEY`. An existing profile role takes precedence over stale Auth metadata. Projects without profiles use protected `app_metadata.role`. Editable user metadata never grants admin access. The dashboard and Reports page log `Admin role` or `User role` in the browser console after the backend verifies the account. Report downloads are PDF files generated by the backend.

Notifications require no additional SQL. Every signed-in user sees the same account join and report submission events, newest first with older pages. Configure `SUPABASE_SERVICE_ROLE_KEY` in the backend environment only so the server can read all Auth accounts and report event timestamps. Responses include only names, event types, IDs and timestamps; report contents and account emails are excluded. Existing report viewing permissions remain enforced by the reports endpoints. Never expose the service key in frontend configuration. Dates and times display in the viewer's local timezone.
